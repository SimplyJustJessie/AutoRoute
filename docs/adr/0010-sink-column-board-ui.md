# UI: a board of per-sink columns, not a patchbay

**Context.** The user rejected both a literal Helvum port-patchbay (re-exposes port detail the app-granularity rules abstract away; large build) and the plan's fixed two-list layout. They want one column (or row) per Target Sink, into which Sources — including other sinks — are dragged to connect.

**Decision.** The main UI is a horizontally-scrollable **board** with **one column per Target** (a sink, or an app-input target such as Discord). A column's cards are the Sources currently feeding that Target. A persistent **Sources palette** lists every draggable Source (app streams, capture devices, sink monitors); dragging a Source into a column connects it and *leaves it in the palette*, so one Source can populate many columns (fan-out). Each **managed** card corresponds one-to-one with a positive Rule (`sourceMatch → targetMatch`); manual/unsaved cards are external links shown in place and promotable. Removing a card disconnects (delete Rule, or write a Suppression for an external link). Card styling encodes state — managed / manual / unsaved / protected. Everything operates at **app granularity**; channels are paired automatically, so there is no port-level wiring.

**Consequences.** The board is a direct, legible view of the routing: every managed card is a rule, so "what feeds this sink" and "what rules exist" are the same picture. A sink appears both as a column (what feeds it) and as a draggable card (to forward its monitor elsewhere). Reversible if needed, but recorded so a future contributor doesn't "restore" the obvious-looking patchbay the user deliberately rejected.
